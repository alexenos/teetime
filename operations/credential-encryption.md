# Member login encryption (Cloud KMS)

Members' Walden logins are encrypted at rest. Since #242 they are encrypted
with a Cloud KMS key (`terraform/kms.tf`) instead of `CREDENTIAL_ENCRYPTION_KEY`,
a Fernet key the maintainer generated by hand and kept a copy of.

## What this guarantees, and what it does not

- **Guaranteed: nobody holds the key.** KMS key material cannot be exported,
  so there is no file, secret or copy of it anywhere.
- **Guaranteed: every decrypt is recorded,** with the identity that made it.
  Data Access audit logs for `cloudkms.googleapis.com` are on
  (`google_project_iam_audit_config.kms`).
- **Not guaranteed: that nobody *can* read a login.** The service has to
  decrypt a login to use it. The project's Owners (the maintainer, and
  `teetime-build`, which holds `roles/owner`) can grant themselves decrypt, and
  Owner may already include it (not verified). Anyone who can merge to `main`
  can also deploy code that reads a login. The safeguard is that doing either
  leaves a record: a decrypt by a person in the audit log, or a commit on a
  public repository. The maintainer accepted the audit log as the safeguard on
  2026-10-02.

## Who has read a login

Every decrypt, newest first, with who made it:

```bash
gcloud logging read 'protoPayload.serviceName="cloudkms.googleapis.com" AND protoPayload.methodName="Decrypt"' \
  --freshness=30d --limit=50 \
  --format="table(timestamp,protoPayload.authenticationInfo.principalEmail,protoPayload.resourceName)"
```

**Expected principals:**
- `teetime-run@...`: the service and the racer, reading a login to book.
- `teetime-observer@...`: the observer, reading the login of the booking it
  watches.

**Any other principal, above all a person's address, is someone reading a
member's password.**

Encrypt calls (`methodName="Encrypt"`) are logged the same way. Each one is a
login being saved through the setup form.

## The fallback copy, during the move

At the maintainer's request (2026-10-03), the move to KMS has a safety net.
While `CREDENTIAL_ENCRYPTION_KEY` is still mounted, every login written with
KMS also keeps a **Fernet copy** (`member_number_fallback`,
`password_fallback`). If a KMS decrypt fails for any reason (KMS
unreachable, a permissions mistake, a bug), the read falls back to that copy,
so the race still logs in. Each time it does, it logs a warning:

```bash
gcloud logging read 'textPayload:"CREDENTIAL_FALLBACK"' --freshness=7d --limit=20   --format="value(timestamp,resource.type,textPayload)"
```

**A morning that ran on the fallback is a KMS problem to fix, even though the
race went fine.**

**This is a deliberate, temporary step back from the guarantee above.** The
copy can be read with the hand-made key, and that leaves no audit record.
Two consequences:

- **It ends at step 6 below.** Once the key is retired, no copy is written,
  and `clear-fallbacks` deletes the existing ones.
- **Invite new members only after step 6.** Until then, their login would
  get a copy readable with the key the maintainer holds.

## Moving logins to the KMS key

1. **Merge #242.** The apply creates the key ring, the key, its IAM grants and
   the audit config. Nothing uses them yet: `credential_kms_enabled` is off.
   Verify from the build log, as `CLAUDE.md` describes:

   ```bash
   gcloud logging read 'resource.type="build" AND textPayload:"google_kms_crypto_key.walden_logins: Creation complete"' \
     --limit=5 --format="value(timestamp,textPayload)" --freshness=7d
   ```

2. **Turn it on.** Change the default of `credential_kms_enabled` to `true` in
   `terraform/variables.tf`, and merge. From then on every login saved is
   written with KMS. Logins already stored keep decrypting with the Fernet
   key.
3. **Have each existing member re-enter their login,** with `/login` in their
   private chat with the bot (the setup form, #240). This doubles as the
   setup form's first real test.
4. **Confirm no row depends on the Fernet key:**

   ```bash
   poetry run python scripts/add_walden_credential.py list
   ```

   Every row must read `encryption=kms`, and the last line must read `No row
   depends on CREDENTIAL_ENCRYPTION_KEY.` Run this against the production
   database, the same way the script was run before.
5. **Run on KMS for a few mornings, then check that no race needed the
   fallback** (the `CREDENTIAL_FALLBACK` query above should return nothing).
6. **Retire the Fernet key.** First delete the fallback copies:

   ```bash
   poetry run python scripts/add_walden_credential.py clear-fallbacks
   ```

   Then a follow-up change removes
   `CREDENTIAL_ENCRYPTION_KEY` from `terraform/main.tf`, which deletes the
   secret and its versions. It must also loosen the precondition that ties
   `admin_proxy_enabled` to `credential_store_enabled`. Delete any local copy
   in `.env` as well. Until then, the old key could still decrypt those
   members' **old** ciphertexts, if anyone kept a database backup.

## Mechanics

- **Prefixes.** Values written with KMS start with `kms1:`, and Fernet values
  have no prefix. `credential_crypto.decrypt` picks the scheme by prefix.
  `scheme_of` reads only the prefix, which is how `list` reports a row's
  encryption without decrypting anything.
- **Binding.** Each KMS ciphertext is bound to its row and field by
  additional authenticated data (`walden_credentials:<requester>:<field>`).
  A ciphertext copied onto another member's row, or into the other column,
  fails to decrypt.
- **Rotation.** The key rotates every 90 days. Old versions stay enabled, so
  rows written under them keep decrypting.
- **Latency.** KMS is one network call per field. The racer resolves a login
  at 06:28, when it logs in, which is two minutes before the window and never
  inside it.
- **Deletion protection.** The key has `prevent_destroy`, because destroying
  it makes every stored login unreadable, with no recovery.
